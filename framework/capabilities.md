# Capability ownership and composition

One repository/distribution, plugin and release carries three independently
usable capabilities. Physical folders are not the capability boundary. The plugin
(Claude Code, Codex) and the setup's boot skill (OpenCode) make all three available;
neither selects a software workflow.

| Capability | Owns | Depends on |
|---|---|---|
| Knowledge and continuity | Scoped capture, retrieval, validity, navigation, common save/resume/housekeeping | Shared scope, authorization/evidence and host adaptation |
| General reasoning | Council, Frame, Bedrock, independent transport and consolidation | Supplied problem/context, shared evidence and host agent capabilities |
| Software development | Task/plan/spec/code/test/release processes and exact engine state | Continuity and selected reasoning methods |

The small common substrate owns location/privacy, authorization, evidence, host
adaptation and setup. It does not absorb topic policy or engine
interpretation. Users retain one conversational entry and their current folders.

The plugin ships the whole tree; there is no per-capability selection, plugin registry
or independent release. Every path reference in the instruction owners resolves
(`tests/capabilities/test_reference_resolution.py`).

## Entry and result contracts

Common save/housekeeping and generic methods are directly discoverable; the engine
router remains for explicitly selected development. A nonsoftware method never
creates a task/build simply to reason. Supplied context is sufficient without Git
or a user repo. Independent Council uses private temporary complete transport before
Chief consumption; final output remains useful inline. Persistence is caller-owned,
requires authorization, and never turns a proposal into an accepted decision.

Consumer entry files retain concrete intent, navigation, storage rules, language,
authorization and domain meaning. General algorithms point to their canonical owner.
Personal, import-heavy workspaces and separate technical repositories share these
contracts; their different content organization is intentional, not a framework fork.
